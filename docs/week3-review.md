# 3주차 Review Questions

## 1. API 요청의 로딩·성공·실패에 따른 UI

로그인과 회원가입 폼은 입력값을 검사한 뒤 요청합니다. 요청 중에는 버튼 문구를 변경하고 중복 제출을 막습니다. 회원가입에 성공하면 완료 배너를 2초 동안 보여준 후 로그인으로 이동합니다. 로그인 성공 시 토큰을 저장하고 메모 목록을 불러옵니다.

잘못된 로그인 정보와 회원가입 중복 이메일은 오류 문구로 표시합니다. 로그인 중 네트워크 오류는 별도 알림창으로 안내하고, 회원가입 실패는 폼에서 안내합니다. 메모 저장에 실패하면 편집창과 입력값을 유지합니다. 인증이 만료되어 메모 요청에서 401이 오면 토큰을 지우고 로그인 화면을 보여줍니다.

## 2. useState와 Zustand의 차이, 전역 상태 선정

useState는 컴포넌트 안에서 상태를 관리하며, 다른 컴포넌트와 공유하려면 공통 부모로 올리고 props로 전달할 수 있습니다. Zustand는 컴포넌트 밖의 store를 구독하므로 여러 화면에서 같은 상태를 사용할 수 있습니다.

이 앱은 로그인 토큰을 Zustand로 관리합니다. 로그인 화면에서 저장한 토큰을 화면 전환과 메모 API 요청에서 함께 사용하고, 로그아웃이나 401 응답 때도 같은 store를 비웁니다. 입력 중인 제목·본문, 모달 열림 여부처럼 해당 화면에서만 필요한 값은 useState에 두었습니다.

## 3. TypeScript 적용 사례와 정리

Memo, MemoDraft, EditorMemo를 구분했습니다. 서버에서 받은 메모에는 숫자 ID가 있지만 새 메모에는 아직 ID가 없고, 작성 중에는 태그가 미선택일 수 있기 때문입니다. 태그는 daily/work/others로 제한하고, API 요청에서는 DAILY/WORK/OTHER로 변환합니다.

컴포넌트 props와 저장 함수의 Promise 반환 타입을 정의하면서, 저장이 끝나기 전에 화면을 닫는 흐름이나 잘못된 값을 전달하는 부분을 확인하기 쉬워졌습니다. DOM 참조에는 HTMLDialogElement·HTMLInputElement 타입을 지정하고, catch에서는 Error인지 확인한 후 메시지를 읽습니다.

기존 JSX를 옮길 때 배열·null 상태의 타입 추론과 작성 전후 데이터 차이를 구분하는 부분이 까다로웠습니다. 공통 타입을 만들고 새 메모와 저장된 메모의 차이를 명시하는 방식으로 정리했습니다. TypeScript는 서버 응답을 실행 중에 자동 검증하지 않으므로 HTTP 상태, 응답 성공 여부와 주요 값 확인도 함께 필요합니다.
